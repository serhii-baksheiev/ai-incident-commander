## The one-shot hold-out, and why it is one event and not three

`runLiveModelLane` builds its plan with `scenarioSet: 'final-evaluation'`
(`packages/evals/src/live-model-lane.ts:350`), and `final-evaluation` is
calibration ∪ hold-out (`packages/evals/src/benchmark-evaluation.ts:356-357`).
So the model-backed lane, the native LangSmith publication and the declared
one-shot hold-out are **the same execution**, not three that can be scheduled
independently.

Two consequences, both binding on how this gate is run:

1. There is no trial run. Any exploratory invocation of the lane consumes the
   hold-out, which is the one thing AIC-18's description forbids before this
   gate's protocol is frozen.
2. The protocol has to be frozen, and the one-shot property has to be a
   mechanism, **before** the first invocation — not asserted after it.

## What this gate had to build, and the two things it found while building it

The survey that opened this gate said the hold-out's one-shot property was "a
protocol commitment, not a mechanism". That was right, and understated. Two
defects were measured while designing the mechanism, and both change what the
gate had to do.

### The door that was already open

`npm run eval:live-model` is a shipped, repeatable command that runs the
hold-out on every invocation. `LiveModelLanePlan.scenarioSet` is the **literal
type** `'final-evaluation'` (`packages/evals/src/live-model-lane.ts:144`), not
an option, and `final-evaluation` is calibration ∪ hold-out
(`packages/evals/src/benchmark-evaluation.ts:356-357`). Nothing guards it. It
has never run in this repository only because no provider credential existed —
which is an accident of the environment, not a mechanism, and that accident
ended the day this gate was executed.

So guarding a *new* final-evaluation command while leaving that one open would
have locked one door in a two-door room. The corpus becomes a **caller-declared
option** with no default, an omitted one refused exactly as
`createExecutionBenchmarkPlan` already refuses an omitted `scenarioSet`
(`benchmark-evaluation.ts:375-383`), and the diagnostic lane is pointed at
calibration.

### Why the record is not keyed on the commit SHA

The obvious design — refuse a second run at the same commit — does not hold, and
the reason is worth writing down because a future reader will otherwise
reintroduce it.

The run happens at SHA X. The record has to be committed, because a gitignored
record is one `rm` away from a free and invisible re-run. Committing it produces
SHA Y. A re-run at Y is then a re-run at a "new commit" whose only difference is
the evidence file the previous run wrote. **The lock opens itself, once per
re-run, forever.**

The key is a fingerprint over the git object ids of only those paths that can
change what the graph does. Committing the evidence does not move it; editing
`packages/` does. The commit SHA still travels *in* the record — AIC-19 asks for
the exact candidate SHA — but it is attribution, not identity.

The exclusion list is asymmetric on purpose: **omitting a path that does affect
behaviour causes a false refusal, which is safe; including a path that does not
causes a false unlock, which is not.** So the list stays narrow.

### The encoding failures, and the fourth instance of one defect

After the three above, the refusals that remained were the model emitting
malformed JSON. The roles asked for their shape in a sentence — an "Answer
shape:" line and a JSON-only instruction — and then parsed hopefully, first `{`
to last `}`.

The provider offers a mechanism that makes that impossible: `output_config.format`
with a JSON schema. The wire shape was measured against the live API rather than
recalled. All three roles declare one now, and the effect is measurable rather
than argued: **3–4 provider calls per run before, 47 after**, with the model
reaching most of the corpus.

⚠ **This is not tuning, and for a hold-out the distinction is the whole point.**
It does not change what the model is asked to reason about and cannot make a bad
hypothesis good. It removes ENCODING from a lane that exists to measure
investigation quality. A schema-valid answer whose CONTENT the domain rejects is
still refused, and those refusals remain the measurement.

Two properties of the schemas are worth stating:

- **They make provenance unexpressible, which is stronger than refusing it.**
  `additionalProperties: false`, and no `producedBy` / `promptVersion` / `at`, so
  a model cannot claim provenance at all rather than claiming it and being
  caught. The existing refusals stay: the schema is the PROVIDER's guarantee and
  the refusal is ours, and a guard resting on a remote party's promise has one
  owner too few.
- **`discriminatingTests[].input` is a closed shape, and that is a real limit.**
  The API refuses every open form — measured: `additionalProperties: true` is
  "not supported", an empty schema is "not supported", and every `object` must
  set `additionalProperties: false` explicitly. The keys are enumerated from the
  ones the replay corpus uses. The domain types this field `z.unknown()` and
  would accept anything, so the constraint is the schema's: a tool needing
  another key cannot be expressed, which is a false REFUSAL — the safe direction.

**And the fix pass produced the fourth instance of this branch's recurring
defect.** The first version of those schemas hand-wrote the domain's
vocabularies, and one was wrong within the hour: `cost` spelled
`['cheap','moderate','expensive']` where the domain declares
`['cheap','medium','expensive']`. The model answered exactly what the schema
asked for, the domain refused it, and the lane recorded the model arm
unreportable — a harness limitation charged to model quality, again. Every enum
is derived from the exported domain schema now, and the derivation refuses
rather than falling back, because a hand-written default is the second spelling
this exists to prevent.

### Where the fixing stopped, and why there

After those three, the next refusal is the model's own: syntactically invalid
JSON (`"rationale"::"placehol"`), on a run that reached ten completions rather
than three. `investigation-roles.ts` declines a repair round on purpose — "a
role that could re-ask on a refused answer would hide the model-quality signal
the lane is measuring" — so that refusal **is** the measurement, and making it
go away would be the one change this gate must not make.

So the line is: a failure the harness caused is a harness defect and was fixed;
a failure the model caused is evidence and was recorded.

measured, and this row is not being upgraded or downgraded on a partial signal.

Publishing the control arm instead would satisfy both rows on paper and is
exactly what this gate forbids: harness-only results presented as model
judgement quality. The control arm scores a single value of zero on every metric
it emits over this corpus, so that publication would also be uninformative.

**v0.2 is therefore not complete.** The honest next step is a v0.2 repair item
against the reference roles — not a re-run, and not a softer gate.
