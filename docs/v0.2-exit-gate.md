## The one-shot hold-out, and why it is one event and not three

`runLiveModelLane` builds its plan with `scenarioSet: 'final-evaluation'`
(`packages/evals/src/live-model-lane.ts:350`), and `final-evaluation` is
calibration ∪ hold-out (`packages/evals/src/benchmark-evaluation.ts:356-357`).
So the model-backed lane, the native LangSmith publication and the declared
one-shot hold-out are **the same execution**, not three that can be scheduled
independently.

Two consequences, both binding on how this gate is run:

1. There is no trial run. Any exploratory invocation of the lane consumes the
   hold-out, which is the one thing AIC-18's description forbids before this
   gate's protocol is frozen.
2. The protocol has to be frozen, and the one-shot property has to be a
   mechanism, **before** the first invocation — not asserted after it.

## What this gate had to build, and the two things it found while building it

The survey that opened this gate said the hold-out's one-shot property was "a
protocol commitment, not a mechanism". That was right, and understated. Two
defects were measured while designing the mechanism, and both change what the
gate had to do.

### The door that was already open

`npm run eval:live-model` is a shipped, repeatable command that runs the
hold-out on every invocation. `LiveModelLanePlan.scenarioSet` is the **literal
type** `'final-evaluation'` (`packages/evals/src/live-model-lane.ts:144`), not
an option, and `final-evaluation` is calibration ∪ hold-out
(`packages/evals/src/benchmark-evaluation.ts:356-357`). Nothing guards it. It
has never run in this repository only because no provider credential existed —
which is an accident of the environment, not a mechanism, and that accident
ended the day this gate was executed.

So guarding a *new* final-evaluation command while leaving that one open would
have locked one door in a two-door room. The corpus becomes a **caller-declared
option** with no default, an omitted one refused exactly as
`createExecutionBenchmarkPlan` already refuses an omitted `scenarioSet`
(`benchmark-evaluation.ts:375-383`), and the diagnostic lane is pointed at
calibration.

### Why the record is not keyed on the commit SHA

The obvious design — refuse a second run at the same commit — does not hold, and
the reason is worth writing down because a future reader will otherwise
reintroduce it.

The run happens at SHA X. The record has to be committed, because a gitignored
record is one `rm` away from a free and invisible re-run. Committing it produces
SHA Y. A re-run at Y is then a re-run at a "new commit" whose only difference is
the evidence file the previous run wrote. **The lock opens itself, once per
re-run, forever.**

The key is a fingerprint over the git object ids of only those paths that can
change what the graph does. Committing the evidence does not move it; editing
`packages/` does. The commit SHA still travels *in* the record — AIC-19 asks for
the exact candidate SHA — but it is attribution, not identity.

The exclusion list is asymmetric on purpose: **omitting a path that does affect
behaviour causes a false refusal, which is safe; including a path that does not
causes a false unlock, which is not.** So the list stays narrow.
