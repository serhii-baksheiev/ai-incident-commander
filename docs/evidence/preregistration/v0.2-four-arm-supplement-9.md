# Preregistration supplement 9: signal-state routing by signal

Written on 2026-09-29, before any paid run. AIC-142 repairs a routing defect
that the AIC-122 premise audit found, under an owner ruling to fix it rather
than register it as a limit.

Every row of `v0.2-four-arm.md` and supplements 1 to 8 stands as registered,
except where a section below says it replaces one. The replaced rows stay in
their files as written.

## The defect

Supplement 7 registered the route table `investigation-routes-v1`. It sent
every `signal-state` observation to tool `metrics`, whatever its signal. But
`signal-state` is an observation form, not a source family. The frozen,
blind-reviewed observation table records `dependency-health` facts on
`dependencies` calls and `error-rate` facts on `metrics` calls. Because the
planned-replay port keeps the tool a call was recorded on, a
`dependency-health` request routed to `metrics` could only answer
`unavailable`. A `dependencies` request could not be answered at all, since no
route named that tool.

## The repair: replaced

The route table is now `investigation-routes-v2`. It replaces the route-table
row of supplement 7. `signal-state` selects its tool by signal, inside the same
table and the same planner:

| signal | route |
| --- | --- |
| `error-rate` | `metrics` |
| `connection-pool` | `metrics` |
| `worker-saturation` | `metrics` |
| `dependency-health` | `dependencies` |
| `latency` | refused |

Each route takes the request `{ service, window, metric }`. The first three
signals measure the subject's own requests or resources, which is what a
metrics series carries. `dependency-health` is the subject's health as a
dependency, which the dependency source carries. `latency` names two source
families in the current vocabulary: it is metric-native for a service's own
requests, yet the reviewed table records the latency of a service observed
from the dependency source. The vocabulary has no field that tells the two
apart, so a latency observation plans no test rather than falling back to one
of them. No prediction template derives a latency observation.

Every signal is either routed or refused, and nothing else: see
investigation-routes.test.mjs › "every SignalKind appears in
INVESTIGATION_ROUTES.byForm['signal-state'].bySignal exactly once, as a route
or a refusal, and bySignal names no key outside SignalKindSchema — both
directions". A refused signal plans no test and never falls back to another
tool: see investigation-planning.test.mjs › "planInvestigation plans no test
when a bySignal entry refuses the signal, and never falls back to another
tool". The table still names no
corpus value: see investigation-routes.test.mjs › "INVESTIGATION_ROUTES names
no replay-corpus value: no scenario id, evidence id, annotation subject, or
recorded input value".

The planner and the planned-replay port read this one table: see
investigation-routes.test.mjs › "scripts/lane-arms.mjs and
apps/cli/src/commands/investigate.ts each import INVESTIGATION_ROUTES from
@aic/graph and pass that same identifier as routes to
createPlannedReplayExecutor, and neither overrides plan_investigation's routes
on createInvestigationNodes — so the live and replay paths read one shared
table, not two copies".

## What did not change

The repair edits no observation annotation (`observation-annotations-v1`), no
scenario fixture, no structural ground truth, no scenario id, no prediction
template, and no evaluator. No model or provider result informed it: it was
designed and measured with no provider call.

## Reachability after the repair

Measured with no provider call. For each calibration scenario, every request
the route table can form, over the services that scenario's recorded calls
name, the three windows, every routed signal and every log class, went
through the planned-replay port. The requests answered `ok` are pinned by
investigation-plan-execute-wiring.test.mjs › "the route-vocabulary
reachability matrix under investigation-routes-v2: every request the route
table can form for each calibration scenario over its own recorded services,
windows and discriminants, answered through the planned-replay port, equals
the registered literal".

Compared with the same enumeration under `investigation-routes-v1`, the repair
adds exactly one answerable request in each of two scenarios, and removes none:
see investigation-plan-execute-wiring.test.mjs › "under the replaced form-only
table investigation-routes-v1, the same route-vocabulary enumeration answers
exactly the v2 matrix minus its two dependencies/dependency-health requests".

| scenario | request added | answers with |
| --- | --- | --- |
| deployment-caused-incident-a | `dependencies {payments, incident, dependency-health}` | `payments-dependencies-healthy` |
| challenge-keeps-leader | `dependencies {payments, incident, dependency-health}` | `payments-v19-dependencies-healthy` |

The registered plan-only matrix of supplement 7 is unchanged, because no
prediction template derives a `dependency-health` observation: see
investigation-plan-execute-wiring.test.mjs › "no PREDICTION_TEMPLATES
observation is a signal-state observation of dependency-health or latency" and
investigation-plan-execute-wiring.test.mjs › "the plan-only calibration
measurement matrix: deriving, planning and executing each rootCause-carrying
scenario's own root cause through the real planner and port, then evaluating
at REPLAY_AS_OF, equals the registered literal matrix".

## What this means for challenge_effect

On `challenge-keeps-leader`, the one calibration scenario that scores
`challenge_effect`, the graph can now execute a discriminating challenge test
that fetches evidence: the `dependencies` request above. A plan derived from a
template cannot reach it, so only a test the challenge role proposes itself
can. That the graph can execute such a test says nothing about whether a model
will propose it. That choice is what calibration measures.

The challenge role is not yet told the request vocabulary the route table
accepts. That is recorded as AIC-143 and blocks the paid run.

## Candidate identity

The change touches `packages/`, so it moves the candidate fingerprint. Planned
test ids include the route-table version, so every planned test id changes.
