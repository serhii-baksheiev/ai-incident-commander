## Why `supported` is unreachable on this code

`supported` requires at least one confirmed prediction. No path in this code
produces a prediction, so no hypothesis can be confirmed. See
status-rules-v02.test.mjs › "never promotes a corroborated hypothesis to
supported without a confirmed prediction of its own".

## What `corroborated` means

`corroborated` means consistent with the available evidence, independently. It
does not mean the hypothesis survived a prediction test.

- It takes at least two independent medium- or high-strength supports, no
  material contradiction, and no confirmed prediction.
- `supported` keeps its v0.1 meaning: the same requirements, plus at least one
  confirmed prediction.
- See status-rules-v02.test.mjs › "pins the confirmed-prediction boundary
  between supported and corroborated".

The conclusion role is shown a definition of every status. Each definition is
generated from the rule table itself, so the prompt cannot drift from the
rules. See:

- conclusion-role.test.mjs › "a mutated table (minimumIndependentSupports 3)
  yields a different corroborated sentence containing 3, proving the text is
  generated";
- conclusion-role.test.mjs › "propose_conclusion's system prompt contains
  every sentence describeStatusRules(STATUS_RULES[STATUS_RULES_VERSION])
  returns".

## Termination uses corroboration, not prediction-confirmed support

- A sole corroborated leader after at least one challenge round terminates
  `sufficient` — see state-termination.test.mjs › "T5: a sole corroborated
  leader that was never challenged is sufficient once at least one round has
  run".
- A run where nothing reaches corroborated terminates `stalled` — see
  state-termination.test.mjs › "T6: after a round has run, no hypothesis
  reaching corroborated or above is stalled, not sufficient by default".
- Termination reads state, never the scenario id or ground truth — see
  lane-arms.test.mjs › "scriptedNodes(record)'s termination depends on state,
  never on the scenario id or ground truth: a renamed clone of a real
  calibration scenario reaches the same stop kind as the original, and a
  sparse-evidence variant reaches a different one".

## The prediction-gap diagnostic

Calibration reports, for the scripted-control and graph-model arms, how many
runs stopped short of a stronger state because no confirmed prediction exists
(ruling item 7). See prediction-gap.test.mjs › "the live lane reports
predictionGapCounts for the control and model arms, equal to a hand-computed
aggregate of their own results, and reports the measured calibration control
fact that every run stalls with no corroborated hypothesis". The diagnostic:

- **Is not a metric.**
  - It is not compared between arms.
  - It is not part of the control baseline.
  - It is never a feedback row.
  - It is never an AIC-19 quality measure.
  - See prediction-gap.test.mjs › "none of the prediction-gap keys appear in
    BENCHMARK_METRIC_KEYS or BEHAVIOR_METRIC_KEYS", › "none of the
    prediction-gap keys appear in a graph-executed result's metrics or
    behaviorMetrics, in observedBaseline, or in graphVsNaive" and ›
    "persisting a result carrying predictionGap emits no feedback row keyed by
    any prediction-gap field".
- **Counts each flag separately. The five counts are not a partition of the
  runs.** See prediction-gap.test.mjs › "two corroborated hypotheses that
  terminated ambiguous report stalledLeaderLacksConfirmedPrediction on the
  earlier-listed leader".
- **Reports the prediction gap as two counts, read separately and never
  summed.** The option-P decision (ruling item 8) reads both:
  - `stalledLeaderLacksConfirmedPrediction` counts runs that stopped short with
    a corroborated leader that lacked a confirmed prediction;
  - `sufficientFromCorroborated` counts runs that concluded on corroboration
    alone, never on a confirmed prediction.

## Known confound: single decisive evidence

Checked against the fixtures on 2026-09-25:

- In `dependency-caused-incident-b` and `challenge-changes-leader`, only one ok
  evidence item bears on the true cause without being declared misleading. The
  true cause can therefore reach `corroborated` only if the model counts the
  misleading item as support. That same reading is what
  `misleading_evidence_handling` scores down. See prereg-confounds.test.mjs ›
  "dependency-caused-incident-b carries at most one distinct, non-misleading,
  expected ok evidence id (single-decisive-evidence confound)" and ›
  "challenge-changes-leader carries at most one distinct, non-misleading,
  expected ok evidence id (single-decisive-evidence confound)".
- `multiple-plausible-causes` expects `ambiguous`. It carries two ok evidence
  ids in total, so two hypotheses can both be corroborated only if both items
  support both hypotheses. See prereg-confounds.test.mjs ›
  "multiple-plausible-causes carries exactly two distinct ok evidence ids in
  total, in contrast to the single-decisive-evidence scenarios above".

## No fitting

Scenarios and ground truth are not fitted to the new rule. Their bytes are
frozen, and a change to them is a new, dated, preregistered decision, never an
edit. See replay-scenarios.test.mjs › "freezes every v0.2 benchmark scenario
byte for byte, with no id missing and none extra: a change is a new, dated,
preregistered decision, never an edit" and › "freezes STRUCTURAL_GROUND_TRUTH
byte for byte: a change is a new, dated, preregistered decision, never an edit
to fit a status-rules result".
