## What the challenge role is now told

`challenge_hypothesis`'s system prompt carries one more sentence: the requests
a discriminating test may name, with each tool's input keys and the closed
values each key takes. The sentence is:

```text
Each discriminating test must be one of these requests, with exactly these input keys: deployments {service: <service>, window: pre-onset|incident|recovery}; metrics {service: <service>, window: pre-onset|incident|recovery, metric: error-rate|connection-pool|worker-saturation}; dependencies {service: <service>, window: pre-onset|incident|recovery, metric: dependency-health}; logs {service: <service>, window: pre-onset|incident|recovery, query: error|timeout|activity}.
```

See cause-emitting-roles.test.mjs › "describeRequestVocabulary returns the exact
sentence for the INVESTIGATION_ROUTES vocabulary" and cause-emitting-roles.test.mjs
› "challenge_hypothesis' system prompt contains describeRequestVocabulary(v) for
the vocabulary it was given".

The vocabulary is derived from `investigation-routes-v2`, the one route table
supplement 9 registered, and from the domain's closed window, signal and log
class enums. It is not written by hand. It names exactly what the planner can
form from that table, in both directions, and the refused `latency` signal
appears nowhere in it: see request-vocabulary.test.mjs ›
"routeRequestVocabulary(INVESTIGATION_ROUTES) names exactly the (tool, key,
value) triples planInvestigation can form over every ExpectedObservation
variant, in both directions, and latency appears in no entry’s values".

The graph arm and the CLI pass that same derived vocabulary: see
lane-arms.test.mjs › "modelNodes(record, port).challenge_hypothesis's captured
system prompt contains describeRequestVocabulary(routeRequestVocabulary(INVESTIGATION_ROUTES))"
and cli-investigate.test.mjs › "createModelReasoning(fakePort).challenge_hypothesis's
system prompt contains describeRequestVocabulary(routeRequestVocabulary(INVESTIGATION_ROUTES))".

## What the challenge role is not told

The sentence names no service, scenario, evidence id or recorded input, and it
does not say which request would answer on which scenario. `<service>` stands
for whatever service the role chooses from the incident it is shown: see
request-vocabulary.test.mjs › "the vocabulary for INVESTIGATION_ROUTES names no
replay-corpus value: no scenario id, evidence id, annotation subject, or
recorded input value".

## What did not change

The route table, the planner, the planned-replay port, the provider's answer
schema, the observation annotations (`observation-annotations-v1`), the
scenario fixtures, the structural ground truth, the prediction templates and
the evaluators. No model or provider result informed this change: it was
designed and tested with no provider call.

## What this means for `challenge_effect`

Telling the role the vocabulary removes a handicap that did not depend on the
model: a model could not be expected to name a request it had never been
shown. It does not make a discriminating test likely. Whether a model proposes
the `dependencies` request that separates the alternative on
`challenge-keeps-leader`, or any other test that fetches new evidence, is what
calibration measures.
