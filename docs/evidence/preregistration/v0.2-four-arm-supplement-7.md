# Preregistration supplement 7: the planned investigation

Written on 2026-09-29, before any paid run. AIC-125 makes the graph arms
investigate instead of replaying the whole recorded corpus. This supplement
registers what they now see and do.

Every row of `v0.2-four-arm.md` and supplements 1 to 6 stands as registered,
except where a section below says it replaces or adds to one. The replaced rows
stay in their files as written.

## Information mode: replaced

`v0.2-four-arm.md` registered the information mode as `full-dump` on every
report. From this supplement on it is per arm: the graph arms are `planned`,
the naive arm stays `full-dump`, and the report schema version is 3. See
four-arm-lane.test.mjs › "declares informationMode per arm: the graph arms
planned, the naive arm full-dump".

The test that row cited, › "declares informationMode full-dump on every
report", no longer exists; the row above replaces it.

## What the graph arms do

- **They plan.** Each untested prediction's expected observations become
  planned tests through the route table `investigation-routes-v1`, which is
  written from the observation vocabulary and names no corpus value. See
  investigation-routes.test.mjs › "INVESTIGATION_ROUTES names no replay-corpus
  value: no scenario id, evidence id, annotation subject, or recorded input
  value".
- **They execute only what was planned**, plus the challenge round's tests.
  See investigation-plan-execute-wiring.test.mjs › "through the real kernel,
  modelNodes(record, port) on deployment-caused-incident-a produces trials only
  for planned or challenge-derived tests, confirms the deployment prediction
  from the evidence the planned request fetched, and leaves
  trialEvidenceViolations empty".
- **The challenge round plans for its alternative.** See
  challenge-planning.test.mjs › "the challenge round calls plan_investigation
  inline, over the alternative, its derived predictions and the challenge
  role's own discriminating tests: with the canonical derive_predictions and
  plan_investigation, an alternative with cause {component: orders-db,
  mechanism: connection-pool-exhaustion} yields a planned metrics test for
  orders-db/incident/connection-pool, and the round's execute_investigation
  sees the challenge role's own test plus the newly planned one".

## How the recorded corpus answers a planned request

The recorded calls were made with the recorder's own inputs, which a
vocabulary-shaped request does not match. The replay port therefore answers a
planned request with the recorded calls of that tool whose output carries an
observation-table fact about the same quantity: form, subject, window, and
signal or log class. It matches the quantity and never its value. See
planned-replay.test.mjs › "a QUANTITY match is independent of outcome: a
matching fact that contradicts what a hopeful template expected still answers
ok with that fact".

A request with no matching fact is `unavailable`, which never counts as
negative evidence. Two consequences are registered as found:

- **Answerability does not track the ground truth.** See planned-replay.test.mjs
  › "bad-deployment: planning from a deployment-regression hypothesis for
  checkout, executed through the port, answers unavailable for every planned
  test, measured off the frozen corpus (both recorded calls carry no facts)"
  and › "dependency-caused-incident-b: a planned deployment request for
  payments answers ok with the pre-onset deployment fact although the
  scenario's cause is inventory-api, measured off the frozen corpus:
  answerability does not track the ground truth".
- **On this corpus a deployment prediction can be confirmed but not
  refuted.** Every deployment fact in the table counts at least one
  deployment. See investigation-plan-execute-wiring.test.mjs › "every
  deployment-in-window fact in OBSERVATION_ANNOTATIONS counts at least one
  deployment, so no planned deployment request can return an absence".

## The arms no longer see the same evidence: replaced and added

Supplement 5 registered that the scripted-control and graph-model arms receive
identical evidence. From this supplement on, both graph arms run the same
harness and differ only in the four reasoning roles. See live-model-lane.test.mjs
› "swaps exactly the four reasoning roles and leaves the rest of the lifecycle
shared".

Each arm sees what its own plan fetched:

- The graph-model arm sees a subset of the recorded evidence the naive arm
  reads. See investigation-plan-execute-wiring.test.mjs › "for every
  calibration scenario, the model arm's plan-only evidence ids (derive → plan →
  execute for the ground-truth cause) are a subset of the scenario's own
  recorded ok evidence ids, and a strict subset for at least one scenario".
- The scripted-control arm's hypotheses carry no cause, so it plans nothing and
  ends with no evidence. See investigation-plan-execute-wiring.test.mjs ›
  "deployment-caused-incident-a is one scenario giving a strict subset: the
  model arm sees exactly the confirming evidence, the scenario's own recorded
  corpus also carries the dependencies evidence, and the scripted-control arm
  run through the real kernel ends with no evidence at all".

This adds to confound 3 of `v0.2-four-arm.md`. The graph and naive arms now
differ in the information they receive as well as in its presentation, and the
graph arm receives less.

## The control arm and its baseline

The scripted-control arm is still the harness signal. It now measures what the
harness fetches on its own, which is nothing. Every calibration run stops
`tools-unavailable`. See prediction-gap.test.mjs › "the live lane reports
predictionGapCounts for the control and model arms, equal to a hand-computed
aggregate of their own results, and reports the measured calibration control
fact that every run stops tools-unavailable with no corroborated hypothesis".

The final-evaluation control baseline's `termination_correctness` moved from
0.1 to 0. The calibration baseline did not move. See lane-arms.test.mjs › "the
committed control baseline files each equal what the scripted control arm
observes under v0.3 — control-baseline.json for final-evaluation,
control-baseline-calibration.json for calibration — with no axis missing and
none extra". The earlier value is kept in the file's `_history`.

Two rows supplement 2 cited were retitled for the new harness:

- lane-arms.test.mjs › "scriptedNodes(record)'s termination depends on state,
  never on the scenario id or ground truth: …" is now proven on the model arm,
  › "modelNodes(record, port)'s termination depends on state, never on the
  scenario id or ground truth: a renamed clone of a real calibration scenario
  reaches the same stop kind as the original, and a variant with its confirming
  recorded fact removed reaches a different one".
- prediction-gap.test.mjs's calibration control fact now reads "stops
  tools-unavailable" where it read "stalls". That is the row cited above.

## Discriminating credit: replaced

`executedDiscriminatingTrialCount` now counts an `ok` trial of a test the
challenge round created that fetched evidence the run did not already hold. A
replay of evidence the run already holds earns nothing. See
challenge-discriminating-credit.test.mjs › "discriminating credit: a challenge
test whose ok trial fetched only already-held evidence (empty evidenceIds)
counts 0 — replay must not earn discriminating credit without new evidence" and
› "discriminating credit: a test planned for the alternative in the challenge
round that fetched new evidence counts".

`challenge_effect` also still passes on a change of leader or of the leader's
status, with no discriminating trial. That is unchanged in this supplement and
is recorded here as a known limit.
