# Preregistration — v0.2 four-arm evaluation

Committed on 2026-09-24, at `main` 7e44fb9, **before any paid calibration run
that contains the naive arm or the repaired graph arm**. Later results never
rewrite this file. A correction is a new dated file beside this one that names
what it supersedes and why. This file stays as it is.

## The question

Does the graph make the **same model** perform better than a single prompt that
receives the same available telemetry?

## Metrics and where each one applies

Three metrics apply to every scenario: `unsupported_claim_rate` (lower is
better), `evidence_coverage`, and `termination_correctness`. The behaviour
metrics apply only where the committed oracle report
(`docs/evidence/oracle/behavior-evaluators-v0.3.json`) emits them:

- `false_alert_correctness`: false-alert only
- `misleading_evidence_handling`: dependency-caused-incident-b in calibration
- `challenge_effect`: challenge-keeps-leader in calibration

`challenge_effect` is `notApplicable` for the naive arm, because that arm runs
no challenge round. `notApplicable` is never read as zero, missing, refused or
withheld.

Graph-vs-naive is reported as win, tie and loss per metric — see
four-arm-lane.test.mjs › "counts win, tie and loss per metric between the graph
and the naive arm, against the oracle". There are no p-values, no confidence
intervals, no significance claims and no composite score — see
budget-policy.test.mjs › "publishes no composite or aggregate score anywhere in
the report".

Resource axes are reported separately from quality and are never combined with
it: model calls, input tokens and output tokens per arm, from the one usage
ledger both paid arms share — see lane-arms.test.mjs › "each lane command
creates exactly one reference-model port and hands it to both paid arms".

## Expected direction, graph-model vs naive

These are written before any repaired-graph or naive result exists. "Win" means
the graph arm scores better on the named metric, and ties are expected
everywhere else.

| scenario | partition | metric where a difference is expected | expected |
| --- | --- | --- | --- |
| false-alert | calibration | `false_alert_correctness`, `termination_correctness` | **graph wins** (strongest) |
| multiple-plausible-causes | calibration | `termination_correctness` (expected stop `ambiguous`, conclusion `multiple-causes`) | **graph wins** (strongest) |
| dependency-caused-incident-b | calibration | `misleading_evidence_handling` | graph wins (weaker expectation) |
| bad-deployment | calibration | none | tie |
| db-pool-exhaustion | calibration | none | tie |
| deployment-caused-incident-a | calibration | none | tie |
| transient-self-resolved | calibration | none | tie (low confidence) |
| challenge-keeps-leader | calibration | none that both arms score (`challenge_effect` is naive-inapplicable) | tie |
| incomplete-evidence | hold-out | `termination_correctness` (expected stop `stalled`, conclusion `inconclusive`) | **graph wins** (strongest) |
| challenge-changes-leader | hold-out | `misleading_evidence_handling`, `termination_correctness` | **graph wins** (strongest) |

For `evidence_coverage`, no direction is registered. The naive arm sees every
entry at once, while the graph arm reaches evidence step by step, and only
evidence an arm references earns credit. Which of those effects dominates is
not predicted here.

## How results will be read

- **Calibration is diagnostic.** It uses the calibration partition only, and
  no hold-out example is inspected or tuned against. A calibration result can
  motivate a change to the graph. It can never support the final claim.
- **The final measured claim comes only from the one-shot hold-out**, on a
  frozen candidate whose fingerprint is recorded before it runs.
- The oracle must reach its best value on a metric before that metric is
  compared at all — see four-arm-lane.test.mjs › "excludes a metric the oracle
  misses best on from graphVsNaive, while a metric it reaches best on stays". An arm that is refused or unreportable is reported as such,
  never as a score.

## Known confounds

1. **Small n.** There are eight calibration scenarios and two hold-out
   scenarios, at three runs each. A single flipped run moves a win/tie/loss
   count.
2. **The scenarios are authored in this repository, and the hold-out fixtures
   are public source.** The one-shot record shows when the hold-out ran. It
   does not show that nobody read the fixtures.
3. **Presentation differs even though the information is the same.** The naive
   arm receives the full telemetry in one prompt. The graph arm receives the
   same entries through replayed tools across several calls. Any difference
   mixes "graph structure" with "incremental presentation".
4. **Call count differs.** The graph arm makes several model calls per run and
   the naive arm makes one. A graph advantage is therefore not a
   same-compute comparison, which is why the resource axes are reported beside
   quality rather than folded into it.
5. **Sampling is not fixed.** No temperature is sent and the provider's default
   applies to both arms, so repeated runs can differ.
6. **Shared budget order.** The naive arm spends from the shared ledger before
   the graph arm on each lane run — see four-arm-lane.test.mjs › "runs control,
   then oracle, then naive, then model, all over the same plan".
7. **The graph is repaired after this registration.** AIC-119 adds the
   conclusion role and state-driven termination. The directions above are
   registered for the graph as AIC-119 leaves it. Graph results recorded before
   AIC-119 measured a graph whose conclusion was constant, and they say nothing
   about this question.
8. **One model.** A result speaks for `claude-opus-5` under this corpus, not for
   graphs in general.
